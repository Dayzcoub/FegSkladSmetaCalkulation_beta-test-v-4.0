# Definition of Done

Этот документ фиксирует простые правила готовности задач. Цель — защитить проект от хаотичной разработки, но не превратить процесс в бюрократию.

## Главный принцип

Задача считается готовой, если она:

- решает заявленную проблему;
- не ломает уже работающие ключевые потоки;
- не меняет защищённые зоны без прямой задачи;
- проверена на базовом уровне;
- задокументирована, если изменилась логика приложения.

Definition of Done — это не жёсткая клетка, а защитная рамка.

Если появляется новая идея, её можно развивать, но нужно понимать, какую часть проекта она затрагивает и что нельзя случайно сломать.

## Минимальный чек для любой задачи

Перед тем как считать задачу готовой, нужно ответить:

1. Что именно изменилось?
2. Какую проблему это решает?
3. Затронута ли проект-смета?
4. Затронуты ли расчёты, BOM, склад, документы, доступы или backend?
5. Что нужно проверить вручную или командой?

Если задача маленькая и UI-only, ответ может быть коротким. Если задача затрагивает ядро, нужен более внимательный review.

## Protected areas

Эти зоны нельзя менять случайно или «заодно»:

- расчёты Stage / Truss / LED;
- BOM quantities;
- quote totals;
- складские остатки, резервы и выдача;
- backend writes;
- доступы и роли;
- PDF/export totals;
- PWA cache behavior.

Изменять их можно, но только если задача прямо об этом и понятно, как проверять результат.

## UI-задачи

UI-задача считается готовой, если:

- визуально решена поставленная проблема;
- не сломаны основные desktop/mobile сценарии;
- не добавлены лишние inline styles и точечные костыли без необходимости;
- не изменена бизнес-логика, если задача была только про внешний вид;
- не сломаны модалки, таблицы и основные кнопки в затронутом разделе.

Для UI допускается гибкость: если новая идея улучшает UX, её можно пробовать, но без случайного изменения расчётов, склада и backend-flow.

## Логические задачи

Если задача меняет логику приложения, нужно проверить, как она связана с:

- проект-сметой;
- ProjectSection;
- Resource Database;
- quoteRows / bomRows / warehouseRows;
- задачами;
- документами;
- доступами;
- lifecycle проекта.

Не каждая логическая задача должна затрагивать всё это. Но нужно явно понимать, что затронуто, а что нет.

## Задачи по базе ресурсов

Готово, если:

- понятно, какую категорию или тип ресурса затронули;
- не потеряны старые данные;
- учтён статус качества позиции;
- импорт/миграция не ломают существующую базу;
- опасные массовые изменения проходят через preview/dry-run или ручное подтверждение.

## Задачи по складу

Готово, если сохранено правило:

```text
До подтверждения проекта — проверка и планирование.
После подтверждения проекта — резервирование и операционный workflow.
```

Складские изменения не должны тихо менять остатки, резервы или рабочие листы без истории.

## Задачи по доступам

Готово, если не нарушена модель:

```text
базовый профиль + системные права + проектные назначения + ключи доступа + срок действия
```

Проектная роль не должна случайно давать глобальные права.

## Документы и PDF

Готово, если:

- клиент не видит лишние внутренние данные;
- склад не видит маржу по умолчанию;
- технические документы показывают нужные параметры;
- отправленные/подтверждённые документы фиксируются как snapshot, если это важно для задачи.

## Проверки

Минимально перед merge:

```bash
npm run check
npm run build
```

Если задача затрагивает конкретный рабочий flow, нужно вручную проверить этот flow.

Если задача не затрагивает код, а только документацию, достаточно review документа и проверки ссылок/индекса.

## Документация

Документацию нужно обновлять, если изменилась:

- логика приложения;
- жизненный цикл проекта;
- модель доступа;
- складская логика;
- структура данных;
- backend/deployment подход;
- правила работы с документами.

Для мелких UI-багфиксов отдельный документ не нужен.

## Гибкость

Если новая идея не укладывается в текущие документы, это не значит, что её нельзя делать.

Правильный порядок:

1. Обсудить идею.
2. Понять, какую часть архитектуры она меняет.
3. При необходимости обновить документ.
4. Потом писать код.

Документы должны помогать развивать проект, а не запрещать развитие.

## Итоговый закон

Задача готова, когда она решает свою цель, не ломает защищённые зоны, проверена в затронутом сценарии и не противоречит общей архитектуре. Для новых идей допускается изменение архитектуры, но осознанно и через обновление правил, а не случайными правками в коде.
