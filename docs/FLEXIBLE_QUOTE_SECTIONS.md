# Гибкая модель разделов сметы

Этот документ фиксирует принцип: сметчик должен быть гибким проектным сборщиком, а не жёстким набором фиксированных шагов.

## Зачем это нужно

Техпродакшен не ограничивается сценой, фермами, LED, звуком и светом.

В проектах могут появляться:

- шатры;
- подиумы из дерева или бревен;
- лаерные конструкции;
- элементы декора;
- столы и стулья;
- кондиционеры;
- тепловые пушки;
- генераторы;
- ФБС и балласт;
- ограждения;
- бытовки;
- гримёрки;
- клининг;
- охрана;
- подрядные работы;
- любые будущие направления.

Если каждый новый тип добавлять как отдельный жёсткий шаг сметчика, проект снова уйдёт в тупик. Поэтому ядро сметчика должно работать через универсальные разделы проекта.

## Главный принцип

Сметчик должен собирать проект из набора разделов.

```text
Проект-смета
    ├─ Раздел проекта
    ├─ Раздел проекта
    ├─ Раздел проекта
    └─ ...
```

Сцена, фермы, LED, звук, свет, шатры, мебель, генераторы и ручные позиции — это не отдельные независимые миры, а разные типы разделов одной проект-сметы.

## Project Section

Базовая сущность для содержимого сметы — `Project Section` / раздел проекта.

У каждого раздела должны быть общие поля:

- `id` — уникальный идентификатор;
- `type` — тип раздела;
- `kind` — направление или специализация;
- `title` — название в проекте;
- `status` — состояние заполнения раздела;
- `responsibleUserId` — ответственный;
- `source` — источник данных;
- `items` — выбранные позиции или ручные строки;
- `bomRows` — нормализованная комплектация;
- `quoteRows` — строки для КП/внутренней сметы;
- `warehouseRows` — складская потребность;
- `tasks` — задачи, рождающиеся из раздела;
- `documents` — документы/техлисты/вложения;
- `supplierId` / `subrentorId` — внешний поставщик, если применимо;
- `notes` — комментарии;
- `attachments` — фото, схемы, файлы;
- `riskFlags` — признаки технических рисков.

Тип раздела определяет, как он собирается и какие данные отдаёт дальше.

## Типы разделов

### 1. Constructor section

Специализированный конструкторский раздел.

Примеры:

- сцена;
- фермы;
- LED;
- будущий единый 3D-конструктор;
- будущие конструкторы шатров, лаера, подиумов или спецконструкций.

Такой раздел отдаёт:

- геометрию;
- схему;
- технические параметры;
- BOM;
- вес;
- мощность;
- складскую потребность;
- технический лист;
- строки для КП;
- задачи для команды и склада.

Пример:

```text
section.type = constructor
section.kind = truss
```

### 2. Catalog section

Раздел из позиций базы оборудования/ресурсов.

Примеры:

- звук;
- свет;
- бэклайн;
- мебель;
- кондиционеры;
- тепловые пушки;
- генераторы;
- кабели;
- декор;
- шатры;
- ФБС;
- расходники.

Менеджер выбирает позиции из базы, указывает количество, срок, цену и комментарии.

Пример:

```text
section.type = catalog
section.kind = climate
```

### 3. Manual construction section

Ручной конструкционный раздел для нестандартных работ и объектов, которых пока нет в конструкторе.

Примеры:

- подиум из бревен;
- деревянный настил;
- лаерная конструкция;
- декоративная арка;
- спецконструкция;
- временный мостик;
- нестандартный монтажный узел.

Такой раздел должен хранить:

- название конструкции;
- описание;
- размеры;
- материалы;
- количество;
- вес, если известен;
- стоимость;
- поставщика или ответственного;
- фото/референсы;
- комментарии для склада и монтажа.

Пример:

```text
section.type = manual_construction
section.kind = wooden_podium
```

### 4. Service section

Услуги и работы.

Примеры:

- монтаж;
- демонтаж;
- доставка;
- дежурство техника;
- оператор;
- проектирование;
- сварочные работы;
- плотник;
- такелаж;
- охрана;
- клининг.

Услуги могут не иметь складской позиции, но должны попадать в КП, задачи и внутреннюю сводку.

Пример:

```text
section.type = service
section.kind = installation
```

### 5. External supplier section

Раздел внешнего поставщика или подрядчика.

Примеры:

- шатёр у подрядчика;
- генератор у поставщика;
- мебель у агентства;
- декор от декоратора;
- ФБС от подрядчика;
- спецтехника;
- внешняя команда.

У такого раздела должны быть:

- поставщик / субарендатор;
- себестоимость;
- цена клиенту;
- маржа;
- статус подтверждения;
- контакт;
- счёт/договор/документы;
- ответственный.

Пример:

```text
section.type = external_supplier
section.kind = tent
```

### 6. Transport section

Транспорт может быть отдельным разделом или набором транспортных строк.

Должен хранить:

- тип транспорта;
- маршрут;
- город / за город;
- километраж;
- тариф;
- даты и время;
- ответственного;
- комментарии по погрузке и разгрузке.

### 7. Crew section

Команда проекта.

Должна хранить:

- роли;
- назначенных пользователей;
- приглашённых специалистов;
- период доступа;
- стоимость работ;
- задачи;
- клиентское отображение без лишних персональных данных.

## Гибкий состав проекта

Менеджер должен иметь возможность выбирать, какие разделы нужны проекту.

```text
+ Сцена
+ Фермы
+ LED
+ Звук
+ Свет
+ Шатры
+ Генераторы
+ Климат
+ Мебель
+ Декор
+ ФБС / балласт
+ Услуги
+ Ручной раздел
+ Внешний поставщик
```

Проект маленькой поляны может содержать только звук и услугу техника. Большой фестиваль может содержать сцену, фермы, LED, звук, свет, шатры, генераторы, ФБС, мебель, климат, декор, транспорт и команду.

## Универсальный поток раздела

Каждый раздел должен проходить общий поток:

```text
Создать раздел
        ↓
Заполнить данные
        ↓
Сформировать quoteRows / bomRows / warehouseRows
        ↓
Проверить склад и риски
        ↓
Сформировать задачи и документы
        ↓
Попасть в общую проект-смету
```

Не каждый раздел обязан иметь BOM или складские строки. Например услуга может иметь только quoteRows и задачи. Но если раздел содержит физические ресурсы, он должен уметь отдавать складскую потребность.

## Правило для будущего 3D-конструктора

Будущий единый 3D-конструктор должен быть не отдельным вторым приложением, а одним из типов constructor section.

Он может работать:

1. отдельно в быстром режиме;
2. внутри проект-сметы как section constructor;
3. как источник геометрии, BOM, складских потребностей, задач и документов.

## Правило расширения

Новый тип оборудования или направления не должен требовать переписывания ядра сметчика.

Для добавления нового направления нужно:

1. добавить или настроить категорию ресурсов;
2. определить тип раздела проекта;
3. описать поля и технические параметры;
4. определить, какие quoteRows, bomRows, warehouseRows и tasks он отдаёт;
5. добавить UI для заполнения, не ломая существующий поток.

## Итоговый принцип

Сметчик должен быть универсальным production project builder. Специализированные разделы вроде сцены, ферм и LED являются частными случаями общей модели разделов проекта.
