# Single-tenant deployment model

Этот документ фиксирует принцип развёртывания приложения для разных компаний.

## Главный принцип

Базовая модель продукта — не общий multi-tenant SaaS, где много компаний живут в одной общей инсталляции.

Базовая модель — отдельная копия приложения для каждой компании.

```text
Компания A
    свой VPS / сервер
    своя база
    свои файлы
    свои пользователи
    свои настройки
    своя кастомизация

Компания B
    свой VPS / сервер
    своя база
    свои файлы
    свои пользователи
    свои настройки
    своя кастомизация
```

Каждая компания получает закрытую экосистему, установленную на её мощностях или на выделенной инфраструктуре под неё.

## Почему не общий multi-tenant по умолчанию

Для техпродакшена важны:

- закрытость клиентской базы;
- закрытость складских остатков;
- закрытость финансовых данных;
- закрытость поставщиков и субаренды;
- разные процессы у разных компаний;
- разные категории ресурсов;
- разные документы;
- разные роли;
- разные правила склада;
- возможность точечной адаптации.

Общий multi-tenant SaaS усложняет безопасность, поддержку кастомизаций, миграции и ответственность за данные.

Single-tenant модель проще и безопаснее для MVP и первых production-внедрений.

## Что изолируется

У каждой компании должны быть отдельные:

- база данных;
- пользователи;
- роли и права;
- ресурсная база;
- склад;
- проекты;
- клиенты;
- документы;
- файлы и фото;
- 3D-ассеты, если кастомные;
- настройки шаблонов;
- интеграции;
- backup/restore;
- audit log;
- deployment env/secrets.

## Возможность кастомизации

У каждой компании могут отличаться:

- название и бренд;
- шаблоны КП;
- категории ресурсов;
- поля в Resource Database;
- роли и проектные назначения;
- складские процессы;
- тарифы;
- правила субаренды;
- видимость финансов;
- список быстрых разделов;
- документы;
- интеграции;
- домен и PWA-настройки.

Поэтому приложение должно поддерживать company-specific configuration.

Но кастомизация не должна превращаться в хаотичные правки ядра.

Правильная модель:

```text
Core application
    общее ядро
    общая доменная модель
    общие protected flows

Company config
    настройки компании
    категории
    шаблоны
    branding
    feature flags
    custom dictionaries

Company extensions
    точечные расширения, если нужны
```

## Core vs customization

Нельзя для каждой компании переписывать ядро приложения.

Общее ядро должно сохранять:

- Project / ProjectSection / Resource model;
- warehouse workflow;
- access control;
- audit log;
- document snapshots;
- backend controlled writes;
- deployment and backup rules.

Кастомизация должна жить в конфигурации, справочниках, шаблонах и feature flags.

## Feature flags

Для отличий между компаниями нужны feature flags.

Примеры:

- включить/выключить 3D-конструктор;
- включить/выключить быстрые калькуляторы;
- включить/выключить чат;
- включить/выключить offline warehouse queue;
- включить/выключить определённые категории;
- включить кастомный шаблон КП;
- включить интеграцию календаря.

Feature flags должны быть частью company config, а не случайными if-условиями по коду.

## Company config

Компания должна иметь конфигурацию:

- company name;
- public product title;
- logo / branding;
- domain / base URL;
- currency;
- timezone;
- default language;
- document templates;
- enabled modules;
- resource category schemas;
- role presets;
- warehouse settings;
- integration settings;
- backup settings.

Реальные secrets не должны храниться в Git. Они живут в `.env` или защищённом secret storage.

## Deployment variants

### Small company / MVP

```text
1 VPS
    frontend
    backend API
    PostgreSQL
    local file storage or simple object storage
```

### Growing company

```text
stronger VPS
    frontend + backend
managed PostgreSQL / Supabase
object storage
scheduled backups
```

### Large company

```text
frontend/static
backend API
managed PostgreSQL
object storage
background workers
monitoring
backup storage
```

Даже при single-tenant подходе инфраструктуру внутри одной компании можно масштабировать.

## Updates and maintenance

Single-tenant модель требует продуманного обновления.

Нужно различать:

- core updates;
- company config updates;
- database migrations;
- document template updates;
- resource category updates;
- custom extension updates.

Перед обновлением нужно:

- сделать backup;
- проверить миграции;
- проверить company config;
- выполнить smoke checks;
- иметь rollback plan.

## Репозиторий и кастомные ветки

Не нужно плодить полностью независимый код для каждой компании без необходимости.

Рекомендуемая модель:

```text
main/core
    общее ядро

company configs
    отдельные конфигурации компаний

custom branches/extensions
    только если кастомизация не решается конфигом
```

Если кастомизация полезна всем, её нужно возвращать в core как feature/config option.

## Data ownership

Данные компании принадлежат этой компании и находятся в её отдельной инсталляции.

Это упрощает:

- юридическую ответственность;
- безопасность;
- backup/restore;
- перенос на другой сервер;
- кастомизацию;
- отключение/архивацию компании.

## Security impact

Single-tenant не отменяет безопасность.

Всё равно нужны:

- roles and permissions;
- project assignments;
- access keys;
- audit log;
- protected file access;
- secrets outside Git;
- backup security;
- controlled backend writes.

Но single-tenant снижает риск утечки между компаниями, потому что разные компании физически или логически разделены на уровне установки.

## Что не делаем по умолчанию

По умолчанию не строим:

- одну общую базу для всех компаний;
- один общий склад для всех компаний;
- одну общую файловую корзину;
- один общий список пользователей всех клиентов;
- глобальный marketplace данных между компаниями;
- общий SaaS workspace layer как обязательную основу.

Такая модель может появиться когда-нибудь позже, но не является базовым направлением текущей архитектуры.

## Влияние на v5 migration

V5 migration должна учитывать single-tenant подход.

Это значит:

- `workspaceId` может оставаться в модели как технический scope;
- но в одной инсталляции обычно будет один основной workspace/company;
- архитектура не должна зависеть от глобального SaaS multi-tenant слоя;
- company config должен стать важной частью deployment;
- переносимость инсталляции важнее общего SaaS-ядра.

`workspaceId` полезен для внутренней структуры, будущей совместимости и тестовых/dev окружений, но не должен означать, что все компании живут в одной базе.

## Итоговый закон

Каждая компания должна иметь отдельную закрытую копию приложения со своей базой, файлами, пользователями, складом, настройками и возможностью точечной кастомизации. Общее ядро приложения должно оставаться единым и обновляемым, а отличия компаний должны по возможности жить в company config, feature flags, шаблонах, категориях и расширениях, а не в хаотичных правках core-кода.
