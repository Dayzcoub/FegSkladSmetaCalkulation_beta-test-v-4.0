# Импорт и миграция данных

Этот документ фиксирует правила импорта старых и внешних данных в гибкую Resource Database.

## Главный принцип

Импорт не должен быть тупой загрузкой файла напрямую в рабочую базу.

Импорт должен быть управляемым процессом:

```text
Источник данных
    ↓
Предпросмотр импорта
    ↓
Маппинг колонок и категорий
    ↓
Проверка качества
    ↓
Поиск дублей
    ↓
Dry-run
    ↓
Подтверждение
    ↓
Импорт
    ↓
Отчёт
```

Система должна сначала показать, что она собирается сделать, и только после подтверждения менять базу.

## Источники импорта

Система должна поддерживать импорт из разных источников:

- старая EquipmentDatabase приложения;
- Excel;
- CSV;
- JSON;
- архив старой версии приложения;
- ручной список;
- прайс поставщика;
- база подрядчика;
- внешний склад;
- остатки склада;
- категории и технические параметры из сторонних таблиц.

Все источники должны приводиться к единой модели:

```text
ResourceItem
ResourceCategory
technicalSpecs
stockQty
prices
supplier/subrentor
compatibility
qualityStatus
```

## Импорт базы извне

Приложение должно уметь импортировать внешнюю базу оборудования/ресурсов, даже если структура колонок отличается от нашей.

Внешняя база может называться как угодно и иметь свои поля:

```text
Артикул
Код
Наименование
Название
Категория
Группа
Производитель
Модель
Остаток
Цена
Вес
Габариты
Комментарий
```

Поэтому нужен экран маппинга:

```text
Колонка внешнего файла      →      Поле Resource Database
-----------------------------------------------------------
Артикул                     →      code
Наименование                →      name
Группа                      →      categoryId
Остаток                     →      stockQty
Цена проката                →      rentalPrice
Вес                         →      weightKg
```

Если система уверенно распознала колонку, она может предложить маппинг автоматически. Но пользователь должен иметь возможность проверить и исправить соответствие.

## Импорт внешних категорий

Внешняя база может содержать категории, которых ещё нет в системе.

Варианты обработки:

- сопоставить с существующей категорией;
- создать новую категорию;
- импортировать как временную категорию `Unmapped`;
- пропустить строки этой категории;
- отправить категорию на ручную проверку.

Нельзя автоматически создавать важные технические категории без проверки, если они участвуют в конструкторах, складе или расчётах.

## Импорт внешних technical specs

Если во внешней базе есть технические поля, система должна позволять замаппить их в `technicalSpecs` категории.

Примеры:

```text
Длина фермы          → technicalSpecs.length_m
Серия фермы          → technicalSpecs.series
Pixel pitch          → technicalSpecs.pixel_pitch
Мощность генератора  → technicalSpecs.power_kw
Фазы                 → technicalSpecs.phases
Размер шатра         → technicalSpecs.size
Вес ФБС              → technicalSpecs.weight_kg
```

Если category schema ещё не знает такое поле, импорт должен предложить:

- добавить поле в схему категории;
- импортировать как custom spec;
- пропустить поле;
- отправить на ручную настройку категории.

## Миграция старой базы

Старую EquipmentDatabase нужно переносить аккуратно.

Пример:

```text
Старая категория: Фермы
    ↓
Новая ResourceCategory: truss
    ↓
technicalSpecs:
    series
    length_m
    connection
    compatibility_group
    element_type
```

```text
Старая категория: LED
    ↓
Новая ResourceCategory: led_cabinet
    ↓
technicalSpecs:
    pixel_pitch
    cabinet_size
    resolution
    power
    weight
    indoor_outdoor
```

Старая база не должна уничтожаться до проверки результата миграции.

## Неполные позиции

Неполные позиции не удаляются автоматически.

Они импортируются со статусом качества:

- `Готова`;
- `Есть предупреждения`;
- `Не готова`;
- `Архив`.

Примеры:

```text
Ферма без длины
    → импортируется
    → статус: Не готова
    → ограничение: нельзя использовать в автоматическом конструкторе
```

```text
Колонка без фото
    → импортируется
    → статус: Есть предупреждения
    → позицию можно использовать
```

## Дубли

Система должна искать возможные дубли по:

- коду;
- названию;
- производителю + модели;
- категории + ключевым technicalSpecs;
- старому id;
- внешнему id;
- supplier item code.

Возможные действия:

- создать новую позицию;
- обновить существующую;
- объединить;
- пропустить;
- пометить старую как архив;
- связать через replacement/migration map.

Опасные объединения нельзя выполнять полностью автоматически.

Например две фермы 3 м могут быть несовместимы по соединению, даже если названия похожи.

## Dry-run

Перед импортом обязателен dry-run.

Отчёт dry-run должен показывать:

- сколько строк прочитано;
- сколько позиций будет создано;
- сколько позиций будет обновлено;
- сколько строк будет пропущено;
- сколько найдено дублей;
- сколько позиций будут иметь warnings;
- сколько позиций будут not ready;
- какие категории не сопоставлены;
- какие поля не распознаны;
- какие строки имеют blocking errors.

Импорт выполняется только после подтверждения пользователя с нужными правами.

## Import batch

Каждый импорт должен иметь `importBatchId`.

Нужно хранить:

- источник;
- имя файла;
- дата импорта;
- кто импортировал;
- маппинг колонок;
- маппинг категорий;
- количество строк;
- созданные позиции;
- обновлённые позиции;
- пропущенные строки;
- ошибки;
- warnings;
- dry-run report;
- финальный отчёт.

## Откат и архивирование

Для каждого import batch нужна возможность:

- посмотреть отчёт;
- найти созданные позиции;
- найти обновлённые позиции;
- отменить импорт, если это безопасно;
- архивировать импортированные позиции;
- восстановить предыдущие значения для обновлённых позиций, если сохранён snapshot.

Если позиция уже использована в проекте, её нельзя просто удалить. В таком случае используется архивирование или replacement map.

## Права на импорт

Импорт — опасная операция.

Минимальные права:

- `canImportResources`;
- `canApproveImport`.

Отдельные права:

- `canUpdateStock` — импорт/обновление остатков;
- `canUpdatePrices` — импорт/обновление цен;
- `canManageResourceCategories` — создание или изменение категорий;
- `canMergeResources` — объединение дублей;
- `canArchiveResources` — массовое архивирование.

Админ может выполнять все эти действия, но критические действия должны логироваться.

## Импорт складских остатков

Импорт остатков должен быть отдельным режимом.

Он не должен случайно менять карточки ресурсов, если пользователь хотел обновить только количество.

Режимы:

- создать новые позиции;
- обновить карточки ресурсов;
- обновить только остатки;
- обновить только цены;
- обновить technicalSpecs;
- dry-run only.

## Импорт цен

Цены могут быть клиентскими, внутренними, субарендными, закупочными или рекомендованными.

При импорте нужно явно указать, какую цену обновляем.

Нельзя случайно заменить клиентскую цену закупочной или наоборот.

## Импорт от поставщика

Прайс поставщика может импортироваться не как наш склад, а как внешний каталог.

Варианты:

- добавить как supplier catalog;
- добавить как external supplier section source;
- добавить как subrent options;
- добавить в нашу базу только выбранные позиции.

Поставщик не должен автоматически становиться нашим складом.

## Безопасность

Импорт не должен:

- принимать исполняемые файлы;
- выполнять формулы Excel как код;
- хранить секреты из файлов;
- смешивать demo/test data с production;
- менять backend без controlled flow;
- тихо перезаписывать рабочую базу без отчёта.

## Итоговый закон

Импорт и миграция данных должны выполняться через управляемый процесс: загрузка источника, маппинг колонок и категорий, проверка качества, поиск дублей, dry-run, подтверждение, импорт и отчёт. Система должна поддерживать импорт внешних баз с произвольной структурой через настраиваемый маппинг. Неполные позиции не удаляются, а получают статус качества. Каждый импорт должен иметь batch id, историю, отчёт и возможность безопасного отката или архивирования результата.
