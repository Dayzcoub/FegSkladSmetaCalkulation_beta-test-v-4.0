# Ошибки и восстановление

Этот документ фиксирует правила обработки ошибок, частичных сбоев и восстановления операций.

## Главный принцип

Ошибки и сбои должны быть частью архитектуры.

Система не должна:

- терять введённые данные;
- молча выполнять частичные операции;
- скрывать проблемы;
- затирать старые документы при ошибке новой генерации;
- оставлять пользователя в состоянии «непонятно, сохранилось или нет».

Любая важная операция должна иметь понятный результат:

```text
success
partial_success
failed
needs_manual_action
retry_available
```

## Критичные сценарии ошибок

Нужно предусмотреть:

- проект не сохранился;
- КП не сформировалось;
- PDF не сгенерировался;
- файл или фото не загрузились;
- импорт базы упал на середине;
- не создался резерв склада;
- возник конфликт склада;
- не отправилось уведомление;
- не создалось календарное событие;
- backend sync прошёл частично;
- нет интернета;
- пользователь потерял доступ;
- интеграция вернула ошибку.

## Черновик и потеря данных

Если пользователь работает с черновиком, система должна защищать введённые данные.

При ошибке сохранения нужно:

- показать понятное сообщение;
- сохранить локальную копию, если возможно;
- дать повторить сохранение;
- не очищать форму;
- не терять уже введённые разделы и строки.

Особенно важно для длинных смет и проектов с большим количеством разделов.

## Подтверждение проекта

Подтверждение проекта — опасная составная операция.

Она может включать:

```text
зафиксировать проект
создать confirmed snapshot
создать задачи
создать резерв склада
создать календарное событие
отправить уведомления
зафиксировать дефицит и субаренду
```

Если один из шагов упал, система должна показать частичный результат.

Пример:

```text
Проект подтверждён
Резерв склада: ошибка
Календарь: создан
Уведомления: частично отправлены
Действие: повторить резерв / создать задачу менеджеру
```

Нельзя показывать «всё успешно», если часть операции не выполнена.

## Складские ошибки

Складские ошибки нельзя скрывать.

Пример конфликта:

```text
Позиция была доступна при предварительной проверке,
но к моменту подтверждения её зарезервировал другой проект.
```

Система должна:

- не создавать ложный резерв;
- показать конфликт;
- создать задачу ответственному;
- предложить замену или субаренду;
- записать ProjectEvent;
- при необходимости записать audit event.

## Ошибки импорта

Импорт работает через import batch.

Если импорт упал, система должна показать:

- сколько строк обработано;
- что создано;
- что обновлено;
- что пропущено;
- какие строки с ошибками;
- какие warnings;
- что можно откатить или архивировать;
- где посмотреть отчёт.

Dry-run должен ловить максимум ошибок до реального изменения базы.

## Ошибки PDF и документов

Если PDF или документ не сгенерировался:

- проект не должен ломаться;
- старый snapshot не должен затираться;
- пользователь должен увидеть ошибку;
- должна быть возможность повторить генерацию;
- если доступен HTML/preview, его можно оставить;
- важная ошибка должна попасть в ProjectEvent.

Если документ уже был отправлен клиенту, ошибка новой генерации не должна менять отправленную версию.

## Ошибки интеграций

Интеграции ненадёжны по определению.

Календарь, email, push, object storage, SMS, external API or accounting integration могут упасть.

Правило:

```text
Project data remains source of truth.
External integration is an adapter.
Adapter failure must not corrupt the project.
```

Для интеграций нужно хранить статусы:

- `pending`;
- `success`;
- `failed`;
- `retry`;
- `cancelled`.

## Retry and recovery actions

Для важных операций нужны действия восстановления:

- повторить;
- отменить;
- открыть отчёт;
- исправить вручную;
- создать задачу ответственному;
- скачать ошибочные строки;
- запустить dry-run повторно;
- архивировать частично импортированные данные;
- восстановить previous snapshot, если он есть.

## Частичный успех

Операция, состоящая из нескольких шагов, должна уметь возвращать `partial_success`.

Пример:

```text
Проект сохранён
Задачи созданы
Резерв склада не создан
Уведомления не отправлены
```

Такой результат лучше, чем скрытая ошибка.

## История ошибок

Важные ошибки должны попадать в историю:

- ошибка подтверждения проекта;
- ошибка резерва;
- ошибка импорта;
- ошибка генерации документа;
- ошибка интеграции;
- ошибка backend sync;
- конфликт доступа;
- рискованный override.

Мелкие UI-ошибки не нужно записывать в audit log как мусор. Но критические действия должны быть видимыми.

## Offline / connection loss

Если пропал интернет:

- пользователь должен видеть, что система offline;
- черновые изменения по возможности сохраняются локально;
- опасные операции, требующие backend, блокируются или становятся pending;
- после восстановления связи должна быть возможность повторить sync;
- конфликт должен показываться явно.

## Backend sync

Backend sync должен быть восстановимым.

Если sync прошёл частично:

- показать, какие сущности синхронизированы;
- какие упали;
- что можно повторить;
- какой payload был отправлен;
- какой verification result получен;
- записать ошибку в sync log.

## User-facing error messages

Сообщение об ошибке должно быть понятным:

Плохо:

```text
Error: undefined failed
```

Хорошо:

```text
Не удалось создать резерв склада. Позиция уже занята другим проектом на выбранную дату. Проверьте дефицит или выберите субаренду.
```

## Правило для разработчиков

Если задача добавляет важную операцию, нужно подумать:

1. Что будет при ошибке?
2. Можно ли повторить операцию?
3. Что уже успело измениться?
4. Нужно ли событие ProjectEvent?
5. Нужно ли audit log?
6. Как пользователь поймёт, что делать дальше?

## Итоговый закон

Система должна быть восстановимой. Важные операции должны иметь статус, возможность повтора, отчёт и запись в ProjectEvent/AuditLog при необходимости. Частичные операции должны быть явно видимыми. Интеграции, PDF, импорт, складские резервы и backend sync не должны ломать проект при сбое и не должны скрывать проблемы от пользователя.
