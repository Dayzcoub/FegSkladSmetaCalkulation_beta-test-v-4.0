# Управление доступом, профили и проектные роли

Этот документ фиксирует модель доступа приложения. Главный принцип: пользователь не должен быть жёстко привязан к одной рабочей роли.

В реальном техпродакшене один и тот же человек может в обычной работе оформлять документы и сметы, а в конкретном проекте быть звукорежиссёром, световиком, техником, водителем или совмещать несколько функций.

## Главный принцип

Доступ пользователя складывается из нескольких слоёв:

```text
Итоговый доступ =
    базовый профиль пользователя
    + системные права
    + проектные назначения
    + ключи доступа
    + срок действия доступа
    - ограничения workspace / проекта / статуса
```

Администратор является особой системной ролью и имеет полный доступ для управления, настройки, диагностики и контроля целостности системы.

Остальные пользователи получают доступ только по своей повседневной роли, выданным правам, проектному назначению и ключам.

## Термины

### Пользователь

Человек или аккаунт в системе.

Пользователь может быть постоянным сотрудником компании или приглашённым специалистом.

### Базовый профиль

Кто человек в компании в обычной повседневной работе.

Примеры:

- админ;
- менеджер;
- технический директор;
- склад;
- техник;
- директор;
- бухгалтерия / документы;
- приглашённый специалист.

Базовый профиль отвечает на вопрос: кто этот человек в системе обычно?

### Системные права

Что пользователю разрешено делать в приложении независимо от конкретного проекта.

Примеры:

- создавать проекты;
- редактировать сметы;
- видеть клиентские цены;
- видеть внутренние цены;
- управлять складом;
- редактировать базу ресурсов;
- управлять пользователями;
- управлять настройками;
- выполнять backend/sync действия.

Системные права не должны называться проектной ролью. Это отдельный слой доступа.

### Проектное назначение

Связь пользователя с конкретным проектом.

Проектное назначение отвечает на вопрос: кем человек является в этом конкретном проекте?

Один пользователь может иметь несколько проектных назначений одновременно.

Пример:

```text
Пользователь: Иван
Базовый профиль: менеджер

Проект А:
    менеджер проекта
    звукорежиссёр

Проект Б:
    световик

Проект В:
    менеджер проекта
    ответственный за субаренду
```

### Проектная роль

Конкретная функция человека внутри проекта.

Примеры проектных ролей:

- менеджер проекта;
- технический директор проекта;
- звукорежиссёр;
- световик;
- LED-инженер;
- риггер;
- техник сцены;
- складской сборщик;
- водитель;
- монтажник;
- ответственный за субаренду;
- приглашённый специалист;
- наблюдатель проекта.

Проектная роль должна давать доступ только в рамках конкретного проекта, а не глобально по всей компании.

### Ключ доступа

Способ выдать пользователю временный или ограниченный доступ.

Ключ может быть:

- постоянным для сотрудника;
- временным для приглашённого специалиста;
- проектным;
- задачным;
- только на просмотр;
- ограниченным по сроку.

## Администратор

Администратор управляет всей системой в целом и следит за целостностью блоков приложения.

Админ должен иметь доступ ко всему функционалу без ограничений:

- все проекты;
- все клиенты;
- все документы;
- все пользователи;
- все роли и назначения;
- база ресурсов;
- категории;
- склад;
- настройки;
- backend/sync;
- audit log;
- диагностика;
- backup/restore;
- системные панели.

Полный доступ админа не означает отсутствие контроля. Все критические действия администратора должны фиксироваться в audit log.

## Базовые профили не должны ограничивать проектные роли

Постоянный сотрудник может выполнять разные функции в разных проектах.

Пример:

```text
Даниил
Базовый профиль: менеджер / постоянный сотрудник
Системные права: создавать проекты, собирать сметы, видеть цены

В проекте 1:
    менеджер проекта
    звукорежиссёр

В проекте 2:
    световик
    ответственный за площадку

В проекте 3:
    только менеджер проекта
```

Система должна поддерживать маленькую компанию, где один человек делает несколько функций, и крупную компанию, где роли строго разделены.

## Разница между системными правами и проектной ролью

Системные права дают возможности в системе в целом.

Проектная роль даёт доступ к конкретному проекту и задачам.

Пример:

```text
Пользователь не является глобальным складским сотрудником.
Но в конкретном проекте он назначен ответственным за сбор комплекта.

Результат:
    он получает доступ к складскому листу этого проекта,
    но не получает доступ ко всему складу компании.
```

## Проектные роли могут совмещаться

Один пользователь может иметь несколько проектных ролей в одном проекте.

Пример:

```text
Проект: Корпоратив 12 июня
Пользователь: Иван
Проектные роли:
    менеджер проекта
    звукорежиссёр
    ответственный за субаренду
```

Система должна уметь объединять доступы этих ролей в рамках проекта.

## Ограничение проектной роли

Проектная роль не должна автоматически давать глобальные права.

Если пользователь назначен LED-инженером в проекте А, он должен видеть LED-раздел проекта А, свои задачи и нужные документы.

Но он не должен из-за этого видеть:

- все проекты компании;
- всю клиентскую базу;
- все финансы;
- всю ресурсную базу;
- админку;
- чужие задачи и документы без необходимости.

## Действия важнее названий ролей

Доступ должен ограничивать не только разделы интерфейса, но и конкретные действия.

Примеры действий:

- просмотр;
- создание;
- редактирование;
- удаление;
- подтверждение;
- отправка КП;
- экспорт;
- изменение цены;
- просмотр внутренних цен;
- просмотр маржи;
- резерв склада;
- выдача со склада;
- возврат на склад;
- изменение остатков;
- выдача ключа;
- изменение роли;
- backend write.

Например, склад может видеть складской лист и отмечать сборку, но не обязан видеть клиентскую цену и маржу.

## Финансовые разрешения

Финансовые данные нужно отделить от технических и складских.

Отдельные права:

- `canViewClientPrices`;
- `canEditClientPrices`;
- `canViewInternalCosts`;
- `canViewMargin`;
- `canApproveDiscount`;
- `canViewFinancialReports`;
- `canEditSubrentCost`;
- `canEditClientSubrentPrice`.

Технические роли по умолчанию не должны видеть маржу, себестоимость и внутреннюю финансовую кухню, если это не требуется для их работы.

## Складские разрешения

Складские действия должны иметь отдельные разрешения:

- `canViewStock`;
- `canViewProjectPickList`;
- `canReserveStock`;
- `canReleaseReserve`;
- `canIssueItems`;
- `canReturnItems`;
- `canRecordDamage`;
- `canAdjustInventory`;
- `canApproveInventoryAdjustment`.

Обычный складской пользователь может собирать, выдавать и принимать возврат, но корректировка остатков должна быть отдельным правом.

## Ключи доступа

Ключ доступа должен хранить:

- кому выдан;
- кто выдал;
- workspace;
- проект, если доступ проектный;
- роль или набор разрешений;
- срок действия;
- статус: активен / истёк / отозван;
- разрешённые действия;
- историю использования.

Ключ не должен давать больше прав, чем нужно для задачи.

Пример:

```text
Ключ: приглашённый LED-инженер
Проект: Корпоратив 12 июня
Срок: 10.06–13.06
Доступ:
    LED-раздел
    LED-техлист
    задачи по LED
    проектный чат LED
Нет доступа:
    финансы
    все проекты
    вся база клиентов
    глобальный склад
    админка
```

## Приглашённые специалисты

Приглашённый специалист получает ограниченный временный доступ.

Он может видеть:

- назначенный проект;
- свою проектную роль;
- свои задачи;
- нужные технические документы;
- нужные файлы;
- проектный чат или role-room, если включено.

Он не должен видеть лишние коммерческие, административные или складские данные.

## Project assignments как источник задач

Назначение человека на проектную роль должно создавать задачи и уведомления.

Пример:

```text
Назначен техдир проекта
        ↓
Создать задачу обследования площадки
        ↓
Открыть доступ к чек-листу
        ↓
Отправить уведомление
```

```text
Назначен LED-инженер
        ↓
Создать задачи по проверке LED-схемы, питания, подвеса/ног и кабелей
        ↓
Открыть LED-техлист и нужные файлы
```

## Audit log

Все важные действия должны фиксироваться:

- смена базового профиля;
- изменение системных прав;
- назначение проектной роли;
- удаление проектной роли;
- выдача ключа;
- отзыв ключа;
- изменение финансовых прав;
- изменение складских прав;
- подтверждение проекта;
- резерв склада;
- изменение остатков;
- backend write;
- override risk/checklist;
- удаление или архивирование проекта.

## Итоговая модель

```text
User
    базовый профиль
    системные права

ProjectAssignment
    проект
    проектная роль
    срок
    задачи
    project-scoped permissions

AccessKey
    способ входа / приглашения
    срок действия
    ограничения

PermissionSet
    конкретные действия

AuditLog
    история важных действий
```

## Итоговый закон

Пользователь не привязан жёстко к одной роли. В системе у него есть базовый профиль и системные права, а в каждом проекте он получает отдельные проектные назначения. Один человек может совмещать несколько проектных ролей. Администратор имеет полный системный доступ, но все критические действия логируются. Все остальные пользователи получают доступ только по роли, назначению, ключу, сроку и конкретным разрешённым действиям.
