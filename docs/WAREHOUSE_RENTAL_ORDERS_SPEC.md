# Складские заказы / Быстрая выдача

Дата фиксации: 2026-05-24
Статус: концепт для будущего модуля, без реализации в текущем проходе.

## 1. Зачем нужен модуль

В приложении нужно заложить отдельный механизм бронирования и выдачи оборудования со склада без обязательного прохождения полного линейного сметчика.

Реальная складская жизнь не всегда начинается со сметы или большого проекта. Часто нужно быстро оформить выдачу нескольких позиций:

- клиенту в короткую аренду;
- партнёру или субарендатору;
- на тест, ремонт, сервис или диагностику;
- сотруднику или команде на внутреннюю задачу;
- на маленькое мероприятие без полноценного КП;
- как временное перемещение между площадками или складами.

Такой документ должен быть самостоятельным источником резерва склада и участвовать в общей доступности оборудования наравне со сметами, проектами и складскими движениями.

## 2. Рабочее название

Основное название модуля: **Складские заказы**.

Альтернативное название для кнопки или быстрого действия: **Быстрая выдача**.

Рекомендуемый UI-паттерн:

- в разделе `Склад / наличие` добавить кнопку `+ Складской заказ`;
- внутри документа выбрать тип операции;
- сам документ хранить не как смету, а как складский документ.

## 3. Основной сценарий

Пользователь открывает `Склад / наличие` и нажимает `+ Складской заказ`.

Далее заполняет:

1. Тип операции.
2. Кому выдаём.
3. Период бронирования / аренды.
4. Место выдачи и место возврата.
5. Ответственных.
6. Список оборудования.
7. Комментарии и служебные заметки.

После этого документ можно сохранить как черновик, зарезервировать позиции или сразу перевести в статус выдачи.

## 4. Типы операций

Минимальный набор типов:

- `client_rental` — аренда клиенту;
- `subrent_out` — выдача партнёру / субарендатору;
- `internal_issue` — внутренняя выдача сотруднику или команде;
- `test_service` — тест / ремонт / сервис / диагностика;
- `temporary_transfer` — временное перемещение;
- `other` — прочее.

Позже можно добавить отдельные режимы:

- списание;
- потеря;
- повреждение;
- замена позиции;
- выдача расходников без возврата.

## 5. Статусы складского заказа

Нужно разделять резерв и физическую выдачу.

Минимальные статусы:

- `draft` — черновик. Позиции набраны, склад ещё не заблокирован.
- `reserved` — зарезервировано. Позиции уже блокируют доступность склада на указанный период, но физически ещё не выданы.
- `issued` — выдано. Оборудование физически ушло со склада, создано складское движение.
- `partially_returned` — частично возвращено. Часть позиций закрыта возвратом, часть ещё числится выданной.
- `returned` — возвращено полностью. Заказ закрыт нормально.
- `overdue` — просрочено. Дата возврата прошла, есть незакрытые позиции.
- `cancelled` — отменено. Резерв снят, выдача не произошла.

Важно: `reserved` и `issued` не должны быть одним и тем же состоянием.

## 6. Данные шапки документа

Документ должен хранить:

- номер / код складского заказа;
- дату создания;
- автора документа;
- тип операции;
- статус;
- связанный клиент, если есть;
- связанный субарендатор, если есть;
- получатель вручную, если нет записи в базе;
- проект или событие, если применимо;
- дата/время начала резерва;
- дата/время планового возврата;
- фактическая дата/время выдачи;
- фактическая дата/время возврата;
- место выдачи;
- место возврата;
- кто оформил;
- кто выдал;
- кто забрал;
- кто должен принять возврат;
- комментарий;
- внутренние заметки.

## 7. Позиции складского заказа

Форма добавления оборудования должна быть похожа на 7-й шаг сметчика, но без сметной логики.

Рекомендуемые элементы:

- фильтр по разделу / категории;
- поиск по названию, коду, типу;
- количество;
- кнопка `+ Добавить`;
- строки выбранного оборудования.

В каждой строке отображать:

- код позиции;
- название;
- категория / тип;
- запрошенное количество;
- доступно на складе;
- уже зарезервировано на выбранный период;
- свободный остаток;
- конфликт по датам;
- источник закрытия: склад / частично / нет;
- статус строки: можно выдать, частично, нет в наличии;
- комментарий по строке;
- фактически выдано;
- фактически возвращено;
- повреждено / потеряно, если применимо.

## 8. Влияние на складскую доступность

Складская доступность должна учитывать складские заказы так же, как сметы и проекты.

Пример:

- всего на складе: 10 шт;
- зарезервировано по сметам: 4 шт;
- зарезервировано по складским заказам: 3 шт;
- свободно: 3 шт.

Документ в статусе `draft` не влияет на склад.

Документ в статусе `reserved` блокирует свободный остаток на период.

Документ в статусе `issued` дополнительно должен формировать складское движение выдачи.

Документ в статусе `returned` закрывает движение возврата и освобождает оборудование.

Документ в статусе `cancelled` снимает резерв.

## 9. Конфликты и проверки

При добавлении позиции нужно проверять:

- наличие на складе;
- пересечение дат с другими резервами;
- пересечение с активными проектами;
- пересечение с другими складскими заказами;
- активные выдачи без возврата;
- позиции в ремонте или недоступные к выдаче;
- ручные блокировки склада.

Интерфейс должен явно показывать:

- `Можно выдать`;
- `Частично доступно`;
- `Нет свободного остатка`;
- `Конфликт дат`;
- `Позиция уже выдана`;
- `Требуется замена / субаренда`.

## 10. Ответственность и история

Для складского заказа нужно хранить историю действий:

- кто создал;
- кто изменил;
- кто перевёл в резерв;
- кто подтвердил выдачу;
- кто физически выдал;
- кто забрал;
- кто принял возврат;
- кто отметил повреждение;
- кто закрыл документ.

Позже можно добавить:

- подпись получателя;
- подпись кладовщика;
- фото при выдаче;
- фото при возврате;
- акт повреждения;
- акт недостачи.

## 11. Связь с существующими разделами

Модуль должен быть связан с:

- `Склад / наличие` — основной вход и отображение влияния на остатки;
- `База оборудования` — источник номенклатуры;
- `Клиенты` — получатели типа клиент;
- `Субаренда` — получатели типа партнёр/субарендатор;
- `Документы` — будущие акты выдачи/возврата;
- `Отчёты` — аналитика по выданному, просроченному, повреждённому;
- `Команда проекта` — ответственные лица;
- `Сметчик` — общий механизм доступности, но без необходимости создавать смету.

## 13. Интерфейс MVP

MVP можно сделать внутри раздела `Склад / наличие`.

Кнопка:

`+ Складской заказ`

Экран/модалка:

1. Шапка документа.
2. Тип операции.
3. Получатель.
4. Период.
5. Места выдачи/возврата.
6. Ответственные.
7. Таблица оборудования.
8. Итоговые предупреждения.
9. Кнопки:
   - `Сохранить черновик`;
   - `Зарезервировать`;
   - `Выдать`;
   - `Отменить`.

После выдачи добавить действия:

- `Принять возврат`;
- `Частичный возврат`;
- `Отметить повреждение`;
- `Закрыть заказ`.

## 14. Что не делать на первом этапе

На первом этапе не нужно превращать этот модуль в полноценный сметчик.

Не добавлять:

- сложные КП;
- скидки;
- коммерческие предложения;
- монтаж;
- транспорт;
- команду проекта;
- PDF КП.

Это именно складской документ, а не смета.

Позже можно добавить печатные формы:

- акт выдачи;
- акт возврата;
- накладная;
- простой PDF лист передачи оборудования.

## 15. Главное правило реализации

Модуль должен использовать общий механизм доступности склада.

Нельзя делать отдельный локальный учёт, который живёт отдельно от склада.

Все резервы из складских заказов должны быть видны в общей картине доступности оборудования, чтобы сметчик, склад и быстрые выдачи не конфликтовали между собой.
