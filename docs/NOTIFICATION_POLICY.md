# Notification policy

Этот документ фиксирует правила уведомлений, push, email, центра уведомлений и антиспама.

## Главный принцип

Уведомления должны рождаться из системных событий, задач и статусов, а не из хаотичных UI-действий.

```text
ProjectEvent / Task / Status change / Risk / Warehouse event / Access event / Document event / Integration event
        ↓
notification rules
        ↓
recipients
        ↓
priority
        ↓
channel
        ↓
action link / task
```

Система должна не пропускать важное, но не превращаться в спам.

## Источники уведомлений

Уведомления могут создаваться из:

- ProjectEvent;
- ProjectTask;
- изменения статуса проекта;
- назначения роли;
- изменения складского листа;
- дефицита;
- субаренды;
- чек-листа техдира;
- документов;
- комментариев;
- offline queue;
- конфликтов синхронизации;
- access/invite events;
- license events;
- integration events;
- backend/sync errors.

## Уровни приоритета

### Critical

События, требующие быстрого внимания.

Примеры:

- проект подтверждён;
- сегодня отгрузка;
- складской конфликт;
- не создан резерв;
- появился дефицит;
- задача просрочена;
- изменился складской лист после сборки;
- критичная ошибка backend sync;
- истекает лицензия или grace period;
- offline warehouse conflict.

Каналы:

- центр уведомлений;
- push;
- email, если настроено или событие системно важное.

### Action required

Нужно действие, но это не авария.

Примеры:

- техдир назначен на чек-лист;
- менеджеру нужно закрыть дефицит;
- складу нужно собрать комплект;
- LED-инженеру нужно проверить схему;
- водителю назначен маршрут;
- нужно подтвердить субаренду;
- нужно обработать конфликт offline queue.

Каналы:

- центр уведомлений;
- push по настройкам;
- email по настройкам.

### Informational

Просто сообщить.

Примеры:

- КП отправлено;
- документ сформирован;
- комментарий добавлен;
- фото загружено;
- задача выполнена;
- файл синхронизирован.

Каналы:

- центр уведомлений;
- без push по умолчанию.

### Digest

То, что лучше собрать пачкой.

Примеры:

- дневная сводка;
- изменения по проектам;
- закрытые задачи;
- не срочные комментарии;
- обновления базы;
- не критичные system notices.

Каналы:

- email digest;
- центр уведомлений.

## Получатели

Уведомление должно идти только тем, кого событие касается.

Получатели определяются через:

- проектные назначения;
- базовый профиль;
- системные права;
- project role;
- responsibleUserId;
- watchers;
- company notification settings;
- user preferences;
- access key scope.

## Примеры маршрутизации уведомлений

### Проект подтверждён

Получают:

- менеджер проекта;
- техдир, если назначен;
- склад;
- участники проекта;
- директор/наблюдатель, если включено;
- приглашённые специалисты, только в пределах их роли.

### Появился дефицит

Получают:

- менеджер проекта;
- ответственный за субаренду;
- склад, если дефицит складской;
- техдир, если дефицит влияет на техническое решение.

### Назначен техдир

Получают:

- техдир — задача обследовать площадку;
- менеджер — подтверждение назначения.

### Изменился LED-раздел

Получают:

- LED-инженер;
- техдир;
- менеджер, если изменение влияет на стоимость, склад или сроки.

### Склад отметил повреждение

Получают:

- менеджер проекта;
- складской ответственный;
- админ/директор, если повреждение критичное или финансово значимое.

### Offline warehouse sync conflict

Получают:

- пользователь, который выполнил offline-действие;
- складской ответственный;
- менеджер проекта, если конфликт влияет на проект;
- админ, если конфликт системный.

## Каналы уведомлений

### Центр уведомлений

Обязателен для всех типов уведомлений.

Каждое уведомление должно содержать:

- что произошло;
- когда;
- проект;
- раздел проекта, если применимо;
- кто инициировал;
- приоритет;
- статус прочтения;
- ссылку на задачу/проект/документ;
- действие, если оно требуется.

### Push

Используется для важного:

- назначена задача;
- проект подтверждён;
- сегодня отгрузка;
- срочный складской конфликт;
- просрочка;
- critical license/system warning.

Push не должен отправляться на каждое мелкое изменение.

### Email

Используется для:

- приглашений;
- восстановления доступа;
- сводок;
- документов/КП;
- лицензии;
- важных системных событий;
- digest.

### SMS

Только для ограниченных сценариев:

- код подтверждения;
- критическая отгрузка;
- срочная задача;
- аварийное уведомление.

SMS не должен использоваться для обычного информационного шума.

### Messenger integrations

Telegram/WhatsApp и другие мессенджеры могут появиться позже, но только через integration adapter и с учётом безопасности, доступа и антиспама.

## Настройки уведомлений

Нужны уровни настроек:

```text
company-level defaults
role-level defaults
project overrides
user preferences
critical notification rules
```

Компания может настроить, например:

- складу всегда push по отгрузке;
- техдирам push по чек-листам;
- менеджерам email digest вечером;
- директору только critical/financial/risk events;
- приглашённым только project-scoped notifications.

Пользователь может отключать неважные уведомления, но critical/system notifications нельзя полностью отключить, если они связаны с безопасностью, доступом, лицензией или рабочей ответственностью.

## Антиспам

Система должна группировать частые изменения.

Примеры:

```text
В проекте за 5 минут изменили 20 строк
        ↓
одно уведомление: "В проекте изменено 20 позиций"
```

```text
В одной задаче появилось 8 комментариев
        ↓
одно сгруппированное уведомление
```

Механики:

- grouping;
- debounce;
- digest;
- silent updates;
- priority levels;
- per-project mute для не критичного;
- notification batching.

## Уведомления и задачи

Если уведомление требует действия, оно должно вести к задаче или создавать задачу.

Плохо:

```text
Есть проблема со складом.
```

Хорошо:

```text
Дефицит: ферма T29Q 3 м, не хватает 4 шт. Открыть задачу закрытия дефицита.
```

Action-required уведомление должно иметь:

- ответственную роль или пользователя;
- срок, если применимо;
- ссылку на задачу;
- действие;
- статус выполнения.

## Уведомления по lifecycle

### Черновик

Минимальные уведомления:

- назначен техдир;
- нужно обследовать площадку;
- пользователь добавлен в проект;
- требуется заполнить критичные данные.

### КП отправлено

- менеджеру: КП отправлено;
- директору: если нужна проверка суммы/скидки;
- ответственному: если клиент запросил изменения.

### Подтверждено

Основной поток:

- склад получает подготовку;
- участники получают задачи;
- техдир получает контроль;
- менеджер получает checklist подготовки;
- календарь/интеграции создают status notifications.

### Сборка склада

- складу: начать сборку;
- менеджеру: сборка началась или есть проблема;
- техдир/ответственный: если нужна техническая замена.

### Выдано / отгружено

- водителю/ответственному: комплект выдан;
- менеджеру: отгрузка выполнена;
- складу: статус выдачи сохранён.

### Возврат

- складу: принять возврат;
- менеджеру: есть повреждения/недостача;
- ответственному: задачи на ремонт/списание/компенсацию.

## Лицензионные уведомления

Получают админ компании, технический владелец и поддержка, если подключена.

События:

- 30 дней до окончания лицензии;
- 14 дней;
- 7 дней;
- 1 день;
- лицензия истекла;
- grace period заканчивается;
- требуется реактивация установки;
- превышен лимит пользователей;
- недоступен license check.

Обычных пользователей не нужно пугать лицензионными сообщениями, пока система работает и их действия не ограничены.

## Offline queue notifications

Пользователь должен видеть:

- действия ждут синхронизации;
- синхронизация началась;
- операции применены;
- есть конфликт;
- операция отклонена;
- требуется ручное решение.

Пример:

```text
5 складских операций ожидают отправки.
```

```text
3 операции применены, 1 конфликт требует решения.
```

## Integration notifications

Интеграции должны уведомлять о статусах:

- calendar event created;
- calendar sync failed;
- email sent;
- email failed;
- file upload failed;
- PDF generated;
- object storage unavailable;
- backend sync failed.

Интеграционная ошибка не должна ломать проект, но должна быть видимой ответственному.

## Notification storage

Уведомления должны храниться с полями:

- `id`;
- `companyId`;
- `projectId`;
- `sectionId`;
- `taskId`;
- `recipientUserId`;
- `recipientRole`;
- `priority`;
- `channel`;
- `title`;
- `body`;
- `actionUrl`;
- `status`;
- `createdAt`;
- `readAt`;
- `deliveredAt`;
- `sourceEventId`;
- `groupKey`.

## Итоговый закон

Уведомления должны строиться от событий проекта, задач, статусов, складских операций, документов, доступов, лицензий и интеграций. Каждое уведомление должно иметь приоритет, получателей, канал доставки и ссылку на действие. Critical/action-required события могут отправляться push/email, информационные события остаются в центре уведомлений или digest. Система должна группировать частые изменения, не спамить пользователей и учитывать роли, проектные назначения, настройки компании и пользовательские предпочтения. Уведомление, требующее действия, должно вести к задаче или создавать задачу.
