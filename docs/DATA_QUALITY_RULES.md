# Правила качества данных

Этот документ фиксирует правила качества данных для гибкой Resource Database.

## Главный принцип

Позиция базы по умолчанию считается готовой для всех стандартных сценариев, если она нормально заполнена по обязательным полям своей категории.

Не нужно вручную подтверждать отдельную готовность для КП, склада, конструктора, техлиста, логистики и автоматического расчёта.

```text
Позиция заполнена по требованиям категории
        ↓
Статус: Готова
        ↓
Можно использовать в стандартных сценариях
```

Отдельные ограничения появляются только автоматически, если данных не хватает или есть ошибка.

## Общий статус качества

У позиции должен быть один общий статус качества:

- `Готова` — обязательные поля категории заполнены, критических проблем нет.
- `Есть предупреждения` — позицию можно использовать, но есть неполные данные или рекомендации к заполнению.
- `Не готова` — позицию нельзя использовать в стандартных сценариях до исправления критических ошибок.
- `Архив` — позиция больше не используется в новых проектах, но сохраняется для истории.

## Проблемы качества

Проблемы делятся на уровни.

### Info

Не критично, но улучшает качество базы.

Примеры:

- нет фото;
- нет комментария;
- нет производителя;
- нет модели;
- нет вложений.

### Warning

Можно использовать, но система должна предупреждать.

Примеры:

- нет веса;
- нет габаритов;
- нет себестоимости;
- нет упаковки;
- нет складского комментария;
- нет фото для склада.

### Blocking

Позиция не готова к стандартному использованию, пока ошибка не исправлена.

Примеры:

- нет кода;
- нет названия;
- нет категории;
- нет единицы измерения;
- активная складская позиция без количества;
- позиция в категории с обязательными technicalSpecs, но эти поля не заполнены.

## Общие обязательные поля

Для любой активной позиции обязательны:

- код;
- название;
- категория;
- тип ресурса;
- единица измерения;
- статус активности;
- источник: своё / субаренда / услуга / виртуальная позиция, если применимо.

## Категорийные обязательные поля

Категория определяет свои обязательные technicalSpecs.

### Фермы

Для использования фермы как нормальной позиции категории нужны:

- серия;
- тип элемента: прямая / угол / узел / база;
- тип соединения;
- compatibility group;
- вес.

Для прямой фермы дополнительно нужна длина.

Если у фермы нет длины или compatibility group, она не должна использоваться в автоматическом конструкторе ферм.

### LED-кабинеты

Обязательные поля:

- размер кабинета;
- pixel pitch;
- разрешение;
- вес;
- потребление;
- indoor/outdoor;
- тип крепления или замка.

Без этих данных LED-конструктор не сможет корректно считать размер, пиксели, вес и питание.

### Генераторы

Обязательные поля:

- мощность кВт или кВА;
- фазы;
- тип топлива;
- разъёмы;
- вес.

Расход топлива может быть warning, если генератор можно добавить в КП, но нельзя точно рассчитать топливо.

### Шатры

Обязательные поля:

- размер;
- площадь;
- тип каркаса;
- тип тента.

Ветровая нагрузка и балластировка могут быть critical для сложных/уличных проектов, потому что это влияет на безопасность и risk level.

### ФБС / балласт

Обязательные поля:

- вес;
- габариты;
- материал;
- назначение или способ использования.

Способ погрузки может быть warning, если он нужен для логистики.

## Сценарные ограничения

Сценарные ограничения не являются ручными галочками.

Система сама выводит ограничения из качества данных.

Примеры:

```text
Позиция: Ферма T29Q 3 м
Все обязательные поля заполнены
Статус: Готова
```

Такую позицию можно использовать в КП, складе, конструкторе, техлистах и расчётах.

```text
Позиция: Ферма без длины
Статус: Не готова
Ограничение: нельзя использовать в автоматическом конструкторе
```

```text
Позиция: Генератор без расхода топлива
Статус: Есть предупреждения
Ограничение: можно добавить в КП, но расчёт топлива будет неточным
```

## Не создавать лишнюю бюрократию

Пользователь не должен каждый раз вручную подтверждать готовность позиции для разных сценариев.

Правильная модель:

```text
Заполнил позицию по категории
        ↓
Система проверила поля
        ↓
Показала общий статус и список проблем
        ↓
Автоматически разрешила или ограничила использование
```

## Data quality report

В базе ресурсов должен быть отчёт качества данных.

Он должен показывать:

- количество готовых позиций;
- позиции с предупреждениями;
- неготовые позиции;
- архивные позиции;
- дубликаты кодов;
- неполные категории;
- позиции без цены;
- позиции без веса;
- позиции без category-specific required specs.

## Кто может исправлять

Исправление базы должно быть доступно пользователям с правами на управление ресурсной базой.

Изменения важных полей должны попадать в audit log:

- код;
- категория;
- technicalSpecs;
- compatibility group;
- stock quantity;
- цены;
- статус активности.

## Итоговый закон

Если позиция заполнена по обязательным полям своей категории, она по умолчанию считается готовой для использования во всех стандартных сценариях приложения. Отдельные ограничения появляются только при нехватке данных, ошибках категории или специальных ограничениях позиции. Система должна показывать один общий статус качества и список проблем, а не требовать ручных подтверждений готовности для каждого сценария.
