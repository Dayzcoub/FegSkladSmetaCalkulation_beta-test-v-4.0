# Лицензия и установка

Этот документ фиксирует модель лицензирования для single-tenant установок.

## Главный принцип

Лицензия должна быть связана с конкретной компанией и её отдельной инсталляцией приложения.

Базовая модель:

```text
Компания
    ↓
отдельная single-tenant установка
    ↓
companyId + installationId
    ↓
подписанная лицензия
    ↓
разрешённые модули, лимиты, срок действия и поддержка
```

Лицензия не должна быть просто глобальным ключом, который можно бесконтрольно скопировать на любой сервер.

## Company license и installation activation

Нужно разделять два понятия.

### Company license

Право конкретной компании использовать продукт.

Company license описывает:

- компанию;
- срок действия;
- план / тариф;
- доступные модули;
- лимиты пользователей;
- параметры поддержки;
- допустимое количество активных установок;
- условия обновлений.

### Installation activation

Конкретная активированная копия приложения на сервере компании.

Installation activation описывает:

- `installationId`;
- `companyId`;
- домен или base URL;
- сервер / deployment fingerprint, если используется;
- дату активации;
- статус активации;
- последнюю проверку лицензии;
- подписанный license token.

Такой подход позволяет компании иметь лицензию, но контролировать конкретные установленные копии.

## Первичная установка

При установке приложения для компании должен выполняться процесс активации:

```text
Создать компанию
    ↓
Сгенерировать companyId
    ↓
Развернуть отдельную копию приложения
    ↓
Сгенерировать installationId
    ↓
Выпустить или применить license token
    ↓
Активировать модули и лимиты
    ↓
Сохранить данные лицензии в backend/config
```

## Что содержит лицензия

Лицензия должна содержать:

- `licenseId`;
- `companyId`;
- `companyName`;
- `installationId` или список разрешённых активных installationId;
- `licenseStart`;
- `licenseEnd`;
- `licenseStatus`;
- `allowedUsers`;
- `enabledModules`;
- `enabledFeatures`;
- `supportPlan`;
- `allowedDomains`;
- `allowedEnvironments`;
- `maxActiveInstallations`;
- `signature`.

## Подписанный license token

Лицензия должна быть подписанной.

Приложение может локально хранить подписанный license token, чтобы работать без постоянного подключения к лицензионному серверу.

Но секреты подписи не должны находиться во frontend.

Проверки лицензии, влияющие на платные модули и activation, должны выполняться на backend/server side.

## Offline и grace period

Приложение не должно ломаться на площадке из-за временной потери интернета.

Нужен grace period:

```text
Лицензия проверена
    ↓
локальный подписанный token действителен N дней
    ↓
приложение работает автономно
    ↓
при появлении интернета обновляет статус лицензии
```

Если лицензия истекла или слишком долго не проверялась, система должна ограничивать новые действия постепенно, а не уничтожать данные.

Возможные ограничения:

- запрет создания новых проектов;
- запрет добавления новых пользователей;
- отключение платных модулей;
- запрет обновлений;
- предупреждение администратору;
- read-only доступ к существующим данным;
- возможность экспорта данных.

## Перенос на другой сервер

Перенос на новый VPS или сервер должен быть штатным сценарием.

Правильный поток:

```text
Старая установка
    ↓
backup
    ↓
деактивация или перевод old installation в migration mode
    ↓
новый сервер
    ↓
restore data
    ↓
новый installationId или reactivation
    ↓
license activation
    ↓
health checks
```

Перенос сервера не должен требовать покупки новой лицензии, если это та же компания и перенос выполнен по правилам.

## Environments

Для одной компании могут быть разные окружения:

- production;
- staging;
- development/demo.

Лицензия может разрешать:

- одну production-инсталляцию;
- одну staging-инсталляцию;
- локальные dev-инсталляции без production data.

Dev/staging окружения не должны использоваться как нелегальные production-копии.

## Модули и feature flags

Лицензия может управлять доступом к модулям:

- сметчик;
- склад;
- Resource Database;
- документы/PDF;
- offline warehouse queue;
- 3D-конструктор;
- чаты;
- push notifications;
- интеграции;
- advanced analytics.

Feature flags должны быть подписаны или проверяться на backend, чтобы их нельзя было просто включить во frontend.

## Защита от копирования

Абсолютной защиты не существует, особенно если приложение ставится на сервер клиента. Но система должна усложнять несанкционированное использование.

Меры:

- signed license token;
- installationId;
- companyId;
- allowed domains;
- server-side validation;
- контроль количества активных установок;
- audit log activation events;
- обновления только для активных лицензий;
- license status checks;
- отсутствие license secrets во frontend.

## Что нельзя делать

Нельзя:

- хранить приватные ключи лицензирования во frontend;
- делать всю проверку лицензии только на JS-клиенте;
- уничтожать данные клиента при истечении лицензии;
- блокировать доступ к уже созданным критичным данным без возможности экспорта;
- ломать текущий проект на площадке из-за кратковременной потери связи;
- привязывать лицензию настолько жёстко к железу, что нормальный перенос сервера становится невозможным.

## Managed single-tenant install

Для первых внедрений предпочтительна модель managed single-tenant install.

Это значит:

- у компании отдельная копия приложения;
- данные компании изолированы;
- установка и обновления выполняются контролируемо;
- лицензия активируется в момент установки;
- исходники и секреты не передаются бесконтрольно;
- обновления и миграции идут через controlled release process.

## Данные клиента

Истечение лицензии или проблема активации не должны уничтожать данные клиента.

Минимально должны сохраняться:

- read-only доступ администратора;
- возможность экспорта;
- backup/restore;
- история проектов;
- документы;
- складские данные.

Ограничения должны касаться нового использования и платных модулей, а не уничтожения уже созданных данных.

## Итоговый закон

Лицензия выпускается на конкретную компанию и конкретную single-tenant инсталляцию. При первичной установке создаются `companyId`, `installationId` и подписанный license token. Лицензия определяет срок действия, доступные модули, лимиты пользователей, домены/окружения и поддержку. При переносе компании на другой сервер создаётся новая активация или переактивация установки с сохранением лицензии компании и контролируемой деактивацией старой установки. Лицензирование должно защищать продукт от копирования, но не должно ломать работу на площадке, уничтожать данные или мешать штатному backup/restore и migration process.
