# Offline and PWA contract

Этот документ фиксирует правила офлайн-режима, PWA cache и синхронизации локальных действий.

## Главный принцип

Офлайн-режим нужен для работы на площадке, складе и в дороге, но он не должен ломать единую серверную истину.

```text
Offline
    можно смотреть, готовить, фиксировать локальные события

Online sync
    сервер проверяет, применяет, отклоняет или отправляет на ручное решение
```

Офлайн-действия не должны молча считаться окончательной правдой, пока они не синхронизированы и не подтверждены backend-состоянием.

## Режимы работы

### Online

Доступны обычные операции:

- сохранение проекта;
- проверка склада;
- подтверждение проекта;
- создание резерва;
- отправка уведомлений;
- создание календарных событий;
- backend sync.

### Offline draft mode

Нет интернета, но можно работать с локальными черновиками.

Разрешено:

- заполнять черновик проекта;
- делать быстрые расчёты;
- заполнять чек-лист площадки;
- добавлять фото в локальную очередь;
- писать комментарии в локальную очередь;
- готовить изменения для последующей синхронизации.

### Offline read-only mode

Для чувствительных данных может быть доступен только просмотр заранее загруженной информации:

- техлисты;
- КП/PDF;
- складской лист проекта;
- календарные детали проекта;
- загруженные вложения.

### Offline warehouse mode

Складские операции на отгрузке и приёмке могут выполняться офлайн как локальные события очереди.

Разрешено фиксировать:

- сборка позиции;
- выдача / отгрузка;
- получение водителем или ответственным;
- возврат;
- частичный возврат;
- повреждение;
- потеря;
- комментарий склада;
- фото повреждения;
- подпись/подтверждение, если будет реализовано.

Эти действия не меняют серверную базу мгновенно. Они попадают в `offline warehouse operation queue` и применяются после синхронизации.

## Что нельзя делать офлайн как окончательное действие

Без актуального backend-состояния нельзя финально выполнять:

- подтверждение проекта;
- создание реального резерва склада;
- изменение системных ролей и доступов;
- выдачу ключей приглашённым;
- controlled backend writes;
- массовый импорт в рабочую базу;
- удаление/архивирование критичных данных;
- изменение глобальных остатков как мгновенную серверную истину.

Но можно подготовить локальное событие, которое позже будет проверено и применено сервером.

## Offline warehouse operation queue

Складские офлайн-действия должны храниться как события.

Каждое событие должно иметь:

- `localOperationId`;
- `projectId`;
- `warehouseListVersion`;
- `operationType`;
- `resourceItemId`;
- `quantity`;
- `actorUserId`;
- `deviceId`;
- `createdAtLocal`;
- `expectedServerState`, если доступно;
- `attachments`;
- `notes`;
- `syncStatus`.

Примеры `operationType`:

- `pick_item`;
- `issue_item`;
- `return_item`;
- `partial_return`;
- `mark_missing`;
- `mark_damaged`;
- `replace_item`;
- `add_comment`.

## Sync statuses

Офлайн-события должны иметь статусы:

- `queued` — ждёт интернета;
- `syncing` — отправляется;
- `applied` — применено сервером;
- `rejected` — отклонено сервером;
- `conflict` — конфликт с серверной версией;
- `needs_manual_review` — нужно ручное решение;
- `failed_retry_available` — ошибка, можно повторить.

## Синхронизация складских событий

Когда интернет появляется:

```text
offline operation queue
        ↓
server validation
        ↓
check project status / list version / permissions / stock state
        ↓
apply or reject
        ↓
return sync result
        ↓
show report to user
```

Сервер должен проверить:

- имеет ли пользователь право на действие;
- существует ли проект;
- не закрыт ли проект;
- актуальна ли версия складского листа;
- не была ли позиция уже выдана/возвращена;
- не противоречит ли количество серверному состоянию;
- не изменилась ли структура проекта после локальной операции.

## Конфликты

Конфликт возникает, если офлайн-действие противоречит серверу.

Примеры:

- офлайн выдали позицию, но сервер уже отметил её как выданную другим пользователем;
- офлайн приняли возврат, но проект уже закрыт;
- складской лист изменился после того, как устройство ушло офлайн;
- количество в offline operation больше, чем сервер ожидает;
- позиция была заменена в новой версии складского листа.

Конфликт нельзя молча решать перезаписью.

Система должна показать:

- локальное действие;
- серверное состояние;
- причину конфликта;
- варианты: применить как корректировку, отклонить, отправить на ручное решение, создать задачу ответственному.

## Порядок применения offline warehouse events

События должны применяться в порядке создания внутри одного проекта и устройства, если порядок важен.

Например:

```text
issue_item
        ↓
return_item
```

Нельзя применить возврат раньше выдачи, если сервер не знает о выдаче.

## Защита от дублей

Каждое offline событие должно иметь уникальный `localOperationId`, чтобы повторная отправка не создавала дубли.

Backend должен быть идемпотентным:

```text
same localOperationId
        ↓
не применять второй раз
        ↓
вернуть уже известный результат
```

## Фото и вложения

Фото площадки, фото отгрузки, фото повреждений и вложения могут сохраняться офлайн.

Логика:

```text
создать файл локально
        ↓
поставить в upload queue
        ↓
показать статус ожидания
        ↓
загрузить после появления интернета
        ↓
связать fileUrl с project event / warehouse operation
```

Если upload упал, файл не должен пропасть.

## Что кэшировать

Можно кэшировать:

- app shell;
- JS/CSS bundles;
- иконки;
- последние открытые проекты;
- техлисты выбранных проектов;
- складские листы выбранных проектов;
- КП/PDF, если есть право;
- чек-листы;
- 3D-ассеты, если они нужны для проекта;
- шаблоны документов.

Осторожно кэшировать:

- клиентские данные;
- финансовые данные;
- внутренние цены;
- складские остатки;
- персональные данные.

Нельзя кэшировать:

- service role keys;
- private keys;
- production secrets;
- данные чужих проектов без доступа;
- всю базу клиентов без необходимости;
- всю ресурсную базу крупной компании без необходимости;
- demo/test data в production cache.

## PWA cache versioning

PWA cache должен быть версионированным.

При изменении структуры данных нужно предусмотреть:

- cache bump;
- миграцию local storage / IndexedDB;
- очистку несовместимого старого cache;
- защиту от смешивания старого JS с новой моделью данных;
- понятное сообщение пользователю о необходимости обновления.

## Heavy offline data

Нельзя кэшировать всё подряд.

Для больших проектов нужны:

- выборочная загрузка проекта;
- lazy loading документов;
- lazy loading 3D assets;
- pagination для таблиц;
- ограничение размера offline cache;
- ручной режим «сделать доступным офлайн» для проекта.

## User feedback

Пользователь должен видеть:

- online/offline status;
- сколько действий ждёт синхронизации;
- какие действия применены;
- какие упали;
- какие требуют ручного решения;
- когда последний раз проект был синхронизирован.

## Audit and ProjectEvent

После успешной синхронизации важные offline operations должны становиться нормальными ProjectEvents / AuditLog events.

Например:

- выдача оборудования;
- возврат;
- повреждение;
- потеря;
- изменение складского листа;
- risk override;
- offline conflict resolution.

## Итоговый закон

Офлайн-режим нужен не только для просмотра, но и для безопасной фиксации складских операций, чек-листов, фото и комментариев. Складская отгрузка и приёмка могут выполняться офлайн как локальные события очереди, но серверная база меняется только после синхронизации, проверки прав, проверки версии складского листа и обработки конфликтов. Это позволяет работать без интернета на складе и площадке, но не разрушает единую серверную истину.
