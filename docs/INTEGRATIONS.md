# Интеграции

Интеграции должны подключаться через отдельный слой, а не размазываться по UI.

## Потенциальные интеграции

- Google Calendar;
- Apple/Outlook calendar через `.ics`;
- email;
- SMS;
- push notifications;
- Telegram/WhatsApp уведомления, если будет безопасный сценарий;
- Supabase/PostgreSQL;
- object storage;
- PDF/export jobs;
- 1C/бухгалтерия, если потребуется;
- карты/геокодинг;
- external auth providers.

## Главный принцип

```text
Project event / domain action
        ↓
Integration adapter
        ↓
External service
```

UI не должен напрямую выполнять важные интеграционные действия без domain/service layer.

## Calendar

Календарь должен создаваться из Project / CalendarEvent.

При подтверждении проекта создаётся календарное событие. Интеграция может отправить его во внешний календарь, но source of truth остаётся в проекте.

## Notifications

Уведомления должны рождаться из задач, статусов и project events.

Примеры:

- назначен техдир;
- КП отправлено;
- проект подтверждён;
- создан резерв;
- появился дефицит;
- складская сборка началась;
- задача просрочена.

## Email / SMS / Push

Уведомления должны иметь шаблоны, получателей, статус доставки и историю.

## Object storage

Файлы, фото, PDF, 3D-модели и вложения должны поддерживать переход на object storage.

## Accounting / 1C

Если появится бухгалтерская интеграция, она должна получать данные из подтверждённых версий документов и project snapshots, а не из текущего черновика.

## Error handling

Интеграции могут падать. Система должна:

- сохранять статус попытки;
- показывать ошибку;
- позволять повторить;
- не терять проектные данные;
- не считать внешний сервис единственным источником истины.

## Security

Интеграционные ключи должны храниться только в защищённой конфигурации, не во frontend и не в Git.
