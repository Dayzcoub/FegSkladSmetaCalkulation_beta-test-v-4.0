# Testing strategy

Этот документ фиксирует практичную стратегию проверок. Цель — защищать ядро приложения, не превращая разработку в бесконечную бюрократию.

## Главный принцип

Тестирование должно быть пропорционально риску.

```text
UI / text / docs
    лёгкая проверка

Сметчик / база / документы / склад
    рабочий сценарий

Расчёты / BOM / деньги / доступы / backend
    строгая проверка
```

Не все задачи требуют одинаковой глубины проверки. Но изменения в защищённых зонах нельзя принимать только на глаз.

## Базовые проверки

Для кодовых изменений минимально:

```bash
npm run check
npm run build
```

Для документационных изменений достаточно review текста и проверки, что `docs/README.md` обновлён, если появился новый активный документ.

## Уровни проверки

### Level 1 — лёгкая проверка

Для UI, текста, документации, небольших визуальных правок.

Проверить:

- задача решает заявленную проблему;
- затронутый экран не развалился;
- mobile/desktop не сломаны в очевидном месте;
- бизнес-логика не менялась, если задача была UI-only.

### Level 2 — рабочий сценарий

Для сметчика, базы, склада, документов, импортов.

Проверить:

- `npm run check`;
- `npm run build`;
- затронутый рабочий flow вручную;
- что данные доходят до нужного слоя: quoteRows, bomRows, warehouseRows, documents или tasks.

### Level 3 — защищённое ядро

Для расчётов, BOM, денег, склада, доступов, backend writes.

Проверить:

- автоматические или smoke-проверки, если есть;
- ручную проверку ожидаемого результата;
- отсутствие случайных изменений protected areas;
- audit/versioning behavior, если задача связана с рабочим проектом;
- rollback/dry-run логику, если операция опасная.

## Protected test areas

Особенно защищены:

- Stage calculations;
- Truss calculations;
- LED calculations;
- BOM quantities;
- quote totals;
- warehouse availability;
- reservations;
- subrent calculations;
- access control;
- PDF/export totals;
- backend sync/write flow;
- PWA cache behavior.

Если задача затрагивает эти зоны, нужна более строгая проверка.

## Расчёты и BOM

Расчёты должны проверяться отдельно от UI.

Правильный подход:

```text
input data
    ↓
calculator / domain service
    ↓
result
    ↓
expected result
```

Примеры сценариев:

- сцена заданного размера → ожидаемые настилы, ноги, рамы, лестницы;
- ферма/табуретка заданной длины → ожидаемые секции, узлы, базы, вес;
- LED заданного размера → кабинеты, пиксели, мощность, вес, Hanging Bar.

## Сметчик

Сметчик проверяется как project flow:

```text
создать проект
    ↓
указать клиента / площадку / дату
    ↓
добавить раздел
    ↓
получить quoteRows / bomRows / warehouseRows
    ↓
проверить склад
    ↓
сформировать КП / техлист / складской лист
```

Не каждая задача должна прогонять весь flow, но затронутый участок должен быть проверен.

## База ресурсов

Проверять:

- позиция без категории получает blocking problem;
- готовая позиция по категории считается готовой по умолчанию;
- warning не блокирует использование без причины;
- дубли не объединяются молча;
- импорт проходит через preview/dry-run;
- внешняя база не перезаписывает рабочую базу без подтверждения.

## Склад

Главное правило склада:

```text
До подтверждения проекта — проверка и планирование.
После подтверждения проекта — резервирование и операционный workflow.
```

Проверять:

- проверка наличия не меняет остатки;
- подтверждение проекта создаёт резерв;
- дефицит создаёт задачу;
- изменение проекта после сборки создаёт новую версию складского листа;
- выдача/возврат фиксируются в истории.

## Доступы

Проверять:

- проектная роль не даёт глобальные права;
- приглашённый видит только свой проект/задачи/документы;
- техник не видит маржу по умолчанию;
- склад не меняет цены без прав;
- админ видит всё;
- критические действия пишутся в audit log.

## Документы

Проверять:

- КП не показывает внутреннюю кухню;
- техлист показывает технические параметры;
- складской лист не показывает маржу по умолчанию;
- отправленное КП сохраняется как snapshot;
- изменение после отправки не затирает старую версию.

## Bounded aggregation rule

Сбор информации из сметчика не должен превращаться в бесконечный пересчёт всего приложения.

Проект-смета является центральной сущностью, но это не значит, что каждый экран должен при каждом действии заново обходить все разделы, всю базу ресурсов, весь склад, все документы, задачи, события и файлы.

Правильный подход:

```text
Изменился конкретный раздел
        ↓
пересчитать только этот раздел
        ↓
обновить его normalized output
        ↓
обновить project snapshot / indexes
        ↓
переиспользовать готовые производные данные
```

Неправильный подход:

```text
любой клик
        ↓
пересканировать весь проект
        ↓
пересчитать все разделы
        ↓
перепроверить весь склад
        ↓
пересобрать все документы
        ↓
перерендерить всё приложение
```

Такой подход может повесить приложение на крупных проектах.

## Snapshots and derived data

Для производительности нужно использовать:

- section-level outputs;
- project snapshots;
- cached derived rows;
- dirty flags;
- explicit recalculation points;
- debounced validation;
- background jobs for heavy operations;
- pagination/virtualization for большие таблицы;
- lazy loading для документов, вложений и 3D assets.

Пример:

```text
ProjectSection changed
    ↓
mark section dirty
    ↓
rebuild quoteRows/bomRows/warehouseRows for this section
    ↓
update project totals
    ↓
mark documents as outdated if needed
```

## Heavy operations

Тяжёлые операции не должны запускаться бесконечно или автоматически на каждый ввод символа.

Тяжёлые операции:

- полная проверка склада по большому проекту;
- генерация PDF;
- импорт большой базы;
- поиск дублей;
- пересборка всех документов;
- обработка фото/файлов;
- 3D asset processing;
- backend sync.

Они должны запускаться:

- явно пользователем;
- по debounce;
- в background job;
- через dry-run;
- с прогрессом и возможностью ошибки/повтора.

## Performance checks

Для крупных проектов нужно проверять не только правильность, но и поведение:

- не зависает ли UI;
- не запускается ли бесконечный цикл пересчёта;
- не пересобираются ли все документы при малом изменении;
- не грузится ли вся база там, где нужна одна категория;
- не рендерится ли огромная таблица без pagination/virtualization;
- не кэшируются ли лишние тяжёлые данные в PWA.

## PWA / cache

Если задача не трогает PWA/cache, не нужно лезть в эту область.

Если трогает:

- проверить cache bump;
- проверить обновление приложения;
- убедиться, что demo/test data не попали в production cache;
- не кэшировать чувствительные данные без необходимости.

## Итоговый закон

Тестирование должно защищать проект-смету, расчёты, склад, документы, доступы и backend от случайных поломок. Сбор данных из сметчика должен быть ограниченным и управляемым: пересчитывается то, что изменилось, а тяжёлые операции выполняются явно, по debounce, через snapshot или background flow. Центральная проект-смета не должна превращаться в бесконечный пересчёт всего приложения.
