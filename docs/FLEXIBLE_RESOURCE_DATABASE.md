# Гибкая база ресурсов

Этот документ фиксирует принцип: база оборудования должна быть гибкой ресурсной базой, а не плоской таблицей только для звука, света, сцен и LED.

## Зачем это нужно

В техпродакшене разные категории ресурсов имеют разные важные технические параметры.

У микрофона, фермы, шатра, генератора, кондиционера, тепловой пушки, мебели и ФБС разные характеристики. Если хранить всё в одной плоской таблице с одинаковыми колонками, база быстро станет нечитаемой и неудобной.

Правильная модель:

```text
Ресурс / позиция базы
    ├─ общие поля
    └─ technical_specs по схеме категории
```

## Общие поля позиции

У любой позиции базы должны быть общие складские, коммерческие и идентификационные поля:

- `id` — идентификатор;
- `code` — внутренний код;
- `name` — название;
- `categoryId` — категория;
- `subcategoryId` — подкатегория;
- `resourceType` — тип ресурса;
- `manufacturer` — производитель;
- `model` — модель;
- `unit` — единица измерения;
- `stockQty` — количество на складе;
- `reservedQty` — резерв;
- `availableQty` — доступно;
- `rentalPrice` — цена проката / продажи клиенту;
- `costPrice` — внутренняя себестоимость / закупка / аренда;
- `weightKg` — вес;
- `dimensions` — габариты;
- `power` — базовое потребление, если применимо;
- `supplierId` — поставщик по умолчанию;
- `isActive` — активна ли позиция;
- `photo` / `attachments` — файлы и фото;
- `notes` — комментарии;
- `technicalSpecs` — технические параметры по категории.

## Типы ресурсов

База должна поддерживать не только классическое оборудование.

Типы ресурсов:

- оборудование;
- конструкция;
- материал;
- расходник;
- услуга;
- транспорт;
- внешний ресурс / субаренда;
- комплект;
- виртуальная позиция;
- балласт;
- мебель;
- климат;
- декор.

## Категории как схемы параметров

Категория должна быть не просто текстовым названием, а схемой параметров.

Категория должна описывать:

- название;
- тип ресурса по умолчанию;
- единицу измерения по умолчанию;
- важные технические поля;
- складские поля;
- поля для документов;
- поля для совместимости;
- правила отображения в UI;
- правила попадания в КП, склад и техлист.

Пример:

```text
Категория: Генераторы
resourceType: equipment
unit: шт
technical_specs:
    power_kw
    power_kva
    phases
    fuel_type
    fuel_consumption_l_h
    noise_db
    connector_types
    runtime_hours
```

## Примеры технических параметров по категориям

### Звук

- мощность;

- количество каналов;
- разъёмы;
- потребление;

## UI базы

Интерфейс базы должен быть category-aware.

Это значит:

- общие поля показываются у всех позиций;
- технические поля меняются в зависимости от категории;
- неактуальные поля не должны засорять карточку;
- категория определяет важные поля для таблиц, карточек, импорта и документов;
- добавление новой категории не должно требовать переписывания всей базы.

## Склад и документы

Не все технические параметры нужны везде.

### Для склада важны

- код;
- название;
- количество;
- единица измерения;
- вес;
- габариты;
- упаковка;
- способ погрузки;
- складская зона;
- комментарии.

### Для КП важны

- понятное клиенту название;
- количество;
- единица;
- цена;
- итог;
- краткое описание, если нужно.

### Для техлиста важны

- технические параметры категории;
- потребление;
- вес;
- габариты;
- совместимость;
- риски;
- требования к монтажу.

## Совместимость и альтернативы

Для некоторых категорий база должна хранить compatibility metadata.

Примеры:

- фермы разных производителей одной серии;
- LED-кабинеты и замки;
- процессоры и receiving cards;
- световые приборы и подвесы;
- генераторы и разъёмы;
- шатры и балластировка;
- лаерные системы и узлы.

Совместимость должна быть структурным параметром, а не текстовым комментарием.

## Правило расширения базы

Для добавления новой категории нужно:

1. определить тип ресурса;
2. определить единицу измерения;
3. описать technical_specs;
4. указать, какие поля важны для склада;
5. указать, какие поля важны для КП;
6. указать, какие поля важны для техлиста;
7. определить compatibility rules, если они нужны;
8. добавить UI-схему категории.

## Итоговый принцип

База должна быть не только Equipment Database, а Resource Database. Она должна поддерживать любые проектные ресурсы: оборудование, конструкции, материалы, мебель, климат, генераторы, балласт, расходники, услуги и внешние позиции.
