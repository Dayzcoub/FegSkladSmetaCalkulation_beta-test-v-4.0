# Архитектурная миграция v5

Этот документ фиксирует стратегию перехода от текущего спонтанно выросшего прототипа к устойчивой архитектуре приложения.

## Главный вывод

Текущий проект является ценным рабочим прототипом и источником проверенной бизнес-логики. Его нельзя просто выбросить.

Но текущий подход нельзя бесконечно развивать в том же виде. Если продолжать добавлять новые разделы, склад, задачи, backend, 3D, чаты и документы поверх существующего слоя без архитектурной миграции, проект снова упрётся в тупик.

Правильный путь:

```text
Не переписывать всё с нуля сразу.
Не продолжать хаотично наращивать старую структуру.
Постепенно построить новое ядро рядом со старым кодом.
Переносить проверенную бизнес-логику в новую доменную модель.
```

## Что сохраняем из текущего проекта

Текущий проект нужно использовать как источник уже проверенных решений:

- расчёты сцены;
- расчёты ферм;
- расчёты LED;
- BOM-логика;
- quick/quote различие;
- складская проверка;
- дефицит и субаренда;
- документы и PDF;
- роли и доступ;
- visual adapters;
- Supabase-ready идеи;
- UI/UX решения, которые уже были проверены пользователем.

Эти части нельзя потерять при переходе.

## Что текущая структура плохо выдержит

Текущий проект вырос как browser-first vanilla JS app с большим количеством runtime-модулей и глобальным `window.FEGModules` contract.

Слабые места текущего подхода:

- много логики находится близко к UI;
- много связей через глобальное состояние;
- модули знают друг о друге слишком много;
- нет строгой доменной модели;
- quote, warehouse, documents and backend flows местами связаны исторически;
- сложно безопасно добавлять новые направления вроде шатров, генераторов, ФБС, мебели, климата и 3D;
- backend пока не является полноценным центром данных;
- дальнейший рост без модели Project / Section / Resource усилит хаос.

Проблема не в языке JavaScript как таковом. Проблема в отсутствии строгой архитектурной модели и типизированного доменного слоя.

## Целевая архитектурная идея

Переход должен идти к архитектуре:

```text
Project / Quote as core entity
        ↓
ProjectSection registry
        ↓
Resource Database with category schemas
        ↓
Domain builders
        ↓
Warehouse / Tasks / Documents / Backend
        ↓
UI shell and constructors
```

Текущий UI и модули могут временно использовать новый слой, но новая логика должна постепенно выноситься в доменные сервисы.

## Рекомендуемый стек направления

Не требуется срочно менять язык программирования.

Для будущей устойчивой версии логичен стек:

- TypeScript для доменной модели и shared types;
- browser frontend на React, Vue, Svelte или аккуратном vanilla layer — решение позже;
- Three.js / React Three Fiber для будущего 3D-конструктора;
- PostgreSQL / Supabase для backend data layer;
- server-side controlled write path для опасных операций;
- shared validation schemas для frontend/backend.

Важно: переход к TypeScript и typed domain layer важнее, чем выбор UI-фреймворка.

## Не переписывать с нуля одним рывком

Полная перепись с нуля сейчас опасна:

- можно потерять проверенные формулы;
- можно потерять рабочие BOM-правила;
- можно надолго остаться без работающего приложения;
- можно снова начать проект с красивой структуры, но без реальной бизнес-логики.

Правильный подход — staged migration.

```text
Текущий проект остаётся рабочей базой.
Новое ядро появляется рядом.
Старые модули постепенно подключаются к новому ядру.
Проверенная логика переносится, а не переписывается наугад.
```

## Целевая доменная модель

Нужно ввести и зафиксировать основные доменные сущности:

- `Project` — центральная рабочая сущность;
- `ProjectSection` — универсальный раздел проекта;
- `ResourceItem` — позиция гибкой ресурсной базы;
- `ResourceCategory` — категория с собственной схемой technical specs;
- `QuoteRow` — строка клиентской/внутренней сметы;
- `BomRow` — нормализованная комплектация;
- `WarehouseNeed` — потребность склада;
- `AvailabilityResult` — результат проверки наличия;
- `Reservation` — резерв склада;
- `SubrentPlan` — план закрытия дефицита;
- `ProjectTask` — задача пользователя;
- `ProjectRoleAssignment` — назначение роли;
- `DocumentArtifact` — документ / export;
- `CalendarEvent` — календарное событие проекта;
- `ProjectEvent` — история изменения проекта.

Эти сущности должны стать языком приложения.

## Новый слой данных

До крупных UI-переделок нужно создать новый data/domain layer.

Минимальные модули будущего ядра:

```text
projectStore
sectionRegistry
resourceRegistry
quoteBuilder
bomNormalizer
warehousePlanner
taskBuilder
documentBuilder
calendarBuilder
riskAnalyzer
projectEventLog
```

Эти модули должны быть независимыми от DOM.

UI должен обращаться к ним через понятные функции, а не напрямую собирать бизнес-логику внутри обработчиков кнопок и модалок.

## Миграционный план

### Этап 0. Документировать текущие правила

Статус: начат.

Уже добавлены или добавляются:

- `APP_LOGIC.md`;
- `PROJECT_LIFECYCLE.md`;
- `FLEXIBLE_QUOTE_SECTIONS.md`;
- `FLEXIBLE_RESOURCE_DATABASE.md`;
- `ARCHITECTURE_MIGRATION_V5.md`.

Цель этапа: зафиксировать правила до переписывания кода.

### Этап 1. Ввести доменные типы и схемы

Нужно создать typed/spec layer для:

- Project;
- ProjectSection;
- ResourceItem;
- ResourceCategory;
- QuoteRow;
- BomRow;
- WarehouseNeed;
- Task;
- Document;
- CalendarEvent.

Даже если проект пока остаётся на JS, нужно начать с JSDoc/JSON schema или постепенно перейти к TypeScript.

Результат этапа: приложение получает общий язык данных.

### Этап 2. Создать section registry

Нужно перестать думать о сметчике как о фиксированном наборе шагов.

Нужно создать registry типов разделов:

- constructor;
- catalog;
- manual_construction;
- service;
- external_supplier;
- transport;
- crew.

Каждый section type должен описывать:

- как создаётся;
- какие поля нужны;
- какие quoteRows отдаёт;
- какие bomRows отдаёт;
- какие warehouseRows отдаёт;
- какие tasks может создавать;
- какие riskFlags добавляет;
- какие документы поддерживает.

Результат этапа: новые направления можно добавлять без переписывания ядра сметчика.

### Этап 3. Преобразовать EquipmentDatabase в ResourceDatabase

Нужно сохранить текущую базу, но расширить модель:

- общие поля ресурса;
- category schemas;
- category-specific technicalSpecs;
- правила отображения полей по категории;
- compatibility metadata;
- warehouse/document fields per category.

Результат этапа: база сможет поддержать шатры, генераторы, ФБС, мебель, климат, декор, материалы, услуги и внешние ресурсы.

### Этап 4. Перестроить сметчик вокруг ProjectSection

Текущий quote wizard должен постепенно перейти от фиксированных шагов к гибкому project builder.

Новая структура:

```text
Project setup
    client / venue / date / risk / tech director
Project sections
    dynamic section list
Warehouse and deficit
Tasks and team
Documents
Final summary
```

Старые Stage / Truss / LED разделы должны стать частными section implementations.

Результат этапа: сметчик перестаёт быть жёстким мастером и становится универсальным сборщиком проекта.

### Этап 5. Вынести расчёты из UI

Расчёты сцены, ферм, LED и будущих разделов должны быть отделены от UI.

Нужно двигаться к схеме:

```text
input model
    ↓
domain calculator
    ↓
technical result
    ↓
bomRows / quoteRows / warehouseRows
    ↓
UI render
```

UI не должен быть источником бизнес-истины.

Результат этапа: расчёты можно тестировать отдельно от интерфейса.

### Этап 6. Нормализовать warehouse flow

Склад должен работать по единой модели:

- need;
- availability;
- deficit;
- subrent plan;
- reservation;
- pick list;
- issue;
- return;
- closeout.

Важно сохранить правило:

```text
До подтверждения — проверка и планирование.
После подтверждения — резервирование.
```

Результат этапа: склад перестаёт зависеть от отдельных UI-разделов и работает от нормализованной проектной потребности.

### Этап 7. Ввести project tasks и role matrix

После ProjectSection и lifecycle нужно формализовать:

- какие роли существуют;
- кто что видит;
- какие задачи создаются на каждом статусе;
- какие задачи создаются при подтверждении проекта;
- какие задачи создаются из дефицита, субаренды, склада, чек-листа, документов.

Результат этапа: проект начинает управлять работой людей, а не только считать смету.

### Этап 8. Backend-first controlled data layer

Backend должен стать устойчивым центром данных, но не через хаотичные browser writes.

Нужны:

- нормальная схема PostgreSQL/Supabase;
- server-side controlled write path;
- RLS/workspace scope;
- audit log;
- project events;
- sync queue;
- dry-run and verification;
- migrations.

Результат этапа: подтверждённые проекты, резервы, задачи, документы и события живут в базе, а не только в local runtime.

### Этап 9. Новый 3D-конструктор

3D-конструктор нужно делать только после фиксации ProjectSection и ResourceDatabase.

Он должен быть:

- самостоятельным быстрым инструментом;
- section constructor внутри сметчика;
- источником geometry;
- источником bomRows;
- источником warehouseNeeds;
- источником quoteRows;
- источником technical documents;
- совместимым с ResourceDatabase.

Результат этапа: 3D не становится отдельным приложением, а встраивается в ядро проект-сметы.

## Запреты на время миграции

Чтобы не уйти в тупик, запрещается:

- добавлять новые крупные направления как отдельные жёсткие шаги сметчика;
- добавлять новые категории в базу только через новые плоские поля;
- привязывать документы напрямую к DOM вместо project data;
- делать складские резервы из quick mode;
- внедрять 3D как отдельный второй центр приложения;
- смешивать UI cleanup с изменениями расчётов и склада;
- делать backend writes без controlled flow.

## Что можно делать параллельно

Можно продолжать:

- мелкие багфиксы;
- UI polish без изменения логики;
- документацию;
- локальные проверки;
- улучшение существующих quick calculators;
- подготовку ассетов;
- работу над схемами данных;
- перенос расчётов в чистые функции.

Но новые большие фичи должны проверяться на соответствие v5 migration roadmap.

## Критерий успешного перехода

Переход можно считать успешным, когда:

- проект-смета стала центральной data model;
- сметчик собирается из гибких ProjectSections;
- база стала ResourceDatabase с category schemas;
- расчёты отделены от UI;
- склад работает от нормализованных warehouseNeeds;
- документы строятся из project model;
- задачи и роли связаны с lifecycle;
- backend хранит подтверждённые проекты и события;
- 3D-конструктор встраивается как section, а не отдельный остров.

## Итог

Текущий проект не выбрасывается. Он становится источником проверенной логики.

Дальнейшая разработка должна идти не через наращивание старого хаоса, а через архитектурную миграцию v5: Project → Section → Resource → Warehouse → Tasks → Documents → Backend → 3D.
